### 10. What is an Internet Gateway (IGW)?

An **Internet Gateway (IGW)** is a fully managed AWS networking component that connects an **Amazon VPC** to the **public internet**.\
 
 It enables communication between resources in the VPC and the internet. 
 
 An Internet Gateway is required for EC2 instances in **public subnets** to send and receive internet traffic.

### Key Features

* Connects an Amazon VPC to the public internet.
* Allows both **inbound** and **outbound** internet communication.
* Performs **1:1 Network Address Translation (NAT)** for instances with **public IPv4 addresses**.
* Fully managed by AWS, so no maintenance or scaling is required.
* Must be attached to a VPC before internet access is possible.

### How It Works

1. Create or use an existing **VPC**.
2. Attach an **Internet Gateway (IGW)** to the VPC.
3. Update the VPC's **route table** by adding the default route:

   * `0.0.0.0/0 → Internet Gateway`
4. Launch an EC2 instance in a **public subnet** and assign it a **public IP address** or **Elastic IP**.
5. Configure the **Security Group** and **Network ACL (NACL)** to allow the required inbound and outbound traffic.

### Example

Suppose you launch an EC2 instance to host a website:

* The EC2 instance is placed in a **public subnet**.
* The subnet's route table has the route `0.0.0.0/0 → Internet Gateway`.
* The instance has a **public IP address**.
* Users on the internet can access the website, and the EC2 instance can also access the internet to download updates.

### Interview Answer (1–2 Minutes)

> **An Internet Gateway (IGW)** is a fully managed AWS component that connects an Amazon VPC to the public internet. It allows resources in public subnets to communicate with the internet by enabling both inbound and outbound traffic. To use an Internet Gateway, you attach it to a VPC, add a default route (`0.0.0.0/0`) in the route table pointing to the IGW, assign a public IP or Elastic IP to the EC2 instance, and configure the Security Group and NACL to allow the required traffic. Without an Internet Gateway, resources in a VPC cannot directly access the public internet.

Q10. Does an Internet Gateway allow private subnets to access the internet directly?

Does not allow resources in private subnets to access the internet directly. 

Private subnets typically use a NAT Gateway for outbound internet access.**

### Why?

* An **Internet Gateway (IGW)** provides internet connectivity only for instances that:

  * Have a **public IP address** (or Elastic IP), and
  * Are in a subnet whose route table points to the **IGW**.
* Instances in **private subnets** do **not** have public IP addresses, so they cannot access the internet directly through an IGW.
* If instances in a private subnet need **outbound-only** internet access (for software updates, package downloads, etc.), they use a **NAT Gateway** (or NAT instance) located in a public subnet.

### Interview Answer

> **An Internet Gateway does not provide direct internet access to private subnets. To enable outbound internet access for resources in private subnets, AWS typically uses a NAT Gateway deployed in a public subnet.**

This is the standard and expected explanation in AWS interviews.

## Latency

Latency means the time taken for a request to travel from the user to an AWS service and for the response to come back.

Low Latency: Low latency means there is very little delay between sending a request and receiving the response, so the application responds quickly. For example, 20 ms response time.

High Latency: High latency means there is a larger delay between sending a request and receiving the response, so the application responds slowly. For example, 500 ms response time.

### ALB (Application Load Balancer)
ALB (Application Load Balancer): ALB works at Layer 7 (Application Layer) and is mainly used for HTTP/HTTPS traffic. It understands application-level requests, so it can route traffic based on URL paths, hostnames, HTTP headers, etc. For example, `/users` can go to the User Service and `/orders` can go to the Order Service. ALB distributes traffic across healthy EC2 instances, containers, or IP targets and performs health checks. It is commonly used for web applications, REST APIs, and microservices where intelligent HTTP/HTTPS routing is required.
------------------------------------------
### NLB (Network Load Balancer)
NLB (Network Load Balancer): NLB works at Layer 4 (Transport Layer) and is mainly used for TCP, UDP, and TLS traffic. It focuses on network connections rather than understanding HTTP requests, so it does not provide ALB-style path-based or host-based routing. NLB is designed for very high throughput, large numbers of connections, low network-level latency, and static IP requirements. It is commonly used for TCP/UDP applications, custom network protocols, and high-performance network workloads.

### Why do we select Private EC2 instances as the Target Group instead of Public EC2 instances behind an Application Load Balancer (ALB)?

"We choose private EC2 instances as target group targets because they are not directly accessible from the Internet. The Application Load Balancer is placed in a public subnet and receives all client requests. It then forwards those requests to the private EC2 instances. This architecture improves security by hiding the application servers, prevents users from bypassing the load balancer, and allows the ALB to handle SSL termination, health checks, and traffic distribution. Although AWS allows public EC2 instances in a target group, private EC2 instances are the recommended best practice for production environments."

Why do we remove the subnet from the Launch Template when using an EC2 Auto Scaling Group (ASG)?

"Remove subnet for EC2 Auto Scaling templates" appears because Launch Templates used with Auto Scaling Groups should not have a fixed subnet.

, an Auto Scaling Group is designed to launch instances across multiple subnets and Availability Zones for high availability.

For example:

Launch Template
    │
    ├── AMI
    ├── Instance Type
    ├── Security Group
    └── Key Pair
         │
         ▼
Auto Scaling Group
    ├── Subnet A (us-east-2a)
    ├── Subnet B (us-east-2b)
    └── Subnet C (us-east-2c)

If the Launch Template already contains Subnet A, the ASG cannot freely choose Subnet B or C.




"We remove the subnet from the Launch Template because the Launch Template is only used to define how an EC2 instance should be launched, such as the AMI, instance type, security group, and key pair. The Auto Scaling Group (ASG) decides where to launch the instance by selecting one or more subnets. This allows the ASG to distribute instances across multiple Availability Zones, providing high availability and fault tolerance. If we specify a subnet in the Launch Template, it restricts the ASG to that subnet and reduces its flexibility."

### Question:

When creating an EC2 instance, why do we choose either a public subnet or a private subnet? What happens if we choose each one?

### Answer:

We choose the subnet based on whether the EC2 instance should be accessible from the internet or kept secure inside the VPC.

#### If we choose a Public Subnet:

* The EC2 instance can get a public IP (if enabled).
* It can communicate directly with the internet through the Internet Gateway (IGW).
* We can connect using SSH/RDP from the internet (if Security Group allows).
* Suitable for:

  * Bastion Host
  * Web Server
  * Public-facing Application
  * Load Balancer (ALB)

#### If we choose a Private Subnet:

* The EC2 instance does not get a public IP.
* It cannot receive direct internet traffic.
* Outbound internet access is possible only through a NAT Gateway (if configured).
* Suitable for:

  * Application Server
  * Database Server
  * Backend Services

### Why do we choose only one subnet?

An EC2 instance is launched into one subnet only, and each subnet belongs to one Availability Zone (AZ). Therefore, at the time of launch, you select the subnet where you want the EC2 instance to reside.

### Interview Answer:

> We choose a public subnet when the EC2 instance needs direct internet access, such as a web server or bastion host. We choose a private subnet when the instance should not be directly accessible from the internet, such as an application server or database server. The subnet determines the instance's network connectivity and security.



The subnet we choose depends on whether the EC2 instance should be accessible from the internet.

Public Subnet: We choose a public subnet when the EC2 instance needs direct internet access, such as a web server, bastion host, or load balancer. The subnet has a route to an Internet Gateway, and the instance can have a public IP address.
Private Subnet: We choose a private subnet when the EC2 instance should not be accessible from the internet, such as an application server or database server. The instance has only a private IP address. If it needs internet access for updates, it uses a NAT Gateway.

We select only one subnet while launching an EC2 instance because an EC2 instance can have one primary network interface (primary ENI), and that ENI must belong to one subnet. If we need instances in multiple subnets, we launch multiple EC2 instances or use an Auto Scaling Group.

### Question:

If the Application Load Balancer (ALB) is enabled only in Availability Zones 1a and 1b, but the Auto Scaling Group (ASG) launches an EC2 instance in the private subnet of AZ-1c, what will happen?

### Answer:

The EC2 instance in AZ-1c will launch successfully, but it will not receive any traffic from the ALB.

Reason:

* The ALB is enabled only in AZ-1a and AZ-1b.
* ALB sends traffic only to the Availability Zones that are enabled on it.
* Since AZ-1c is not enabled on the ALB, it cannot forward requests to the EC2 instance in AZ-1c.
* As a result, the EC2 instance remains unused because no user requests reach it.

Interview Answer (Short):

> If the ALB is enabled only in AZ-1a and AZ-1b, the ASG should launch EC2 instances only in those Availability Zones. If an instance is launched in AZ-1c, the ALB cannot send traffic to it because AZ-1c is not enabled on the load balancer. Therefore, the EC2 instance will be running but will not receive any application traffic.

### Question:

What do the Load Balancer (ALB) and Target Group (TG) do?

### Answer:

Load Balancer (ALB):

* Receives requests from users.
* Distributes traffic only to healthy EC2 instances.
* Sends traffic only to the Availability Zones (AZs) that are enabled on the ALB.
* It does not send traffic directly to EC2. It sends traffic through the Target Group.

Target Group (TG):

* Contains the registered EC2 instances (targets).
* Performs health checks on the EC2 instances.
* Reports which instances are Healthy or Unhealthy to the ALB.
* The ALB forwards requests only to the healthy targets in the Target Group.

### Interview Answer:

> The Load Balancer receives user requests and forwards them to the Target Group. The Target Group continuously performs health checks on the registered EC2 instances and tells the Load Balancer which instances are healthy. The Load Balancer then sends traffic only to the healthy EC2 instances in the enabled Availability Zones.

### Question:

What is an AMI?

### Answer:

AMI (Amazon Machine Image) is a pre-configured template used to launch EC2 instances. It contains everything required to create a new server.

---

### Question:

What does an AMI contain?

### Answer:

An AMI contains:

* Operating System (Amazon Linux, Ubuntu, Windows, etc.)
* Installed applications (e.g., Nginx, Apache, Node.js)
* Application code (if already deployed)
* Configuration files
* User data (if configured)

---

### Question:

What is the use of an AMI?

### Answer:

AMI is used to launch new EC2 instances with the same configuration as an existing server. This ensures every new server created by an Auto Scaling Group is identical.

---

### Question:

Does AMI take a backup?

### Answer:

Yes. When you create an AMI from an EC2 instance:

* AWS creates snapshots of the attached EBS volumes.
* These snapshots store the data on the EBS volumes.
* Later, you can launch a new EC2 instance from the AMI, and AWS restores the data from those snapshots.

---

### Interview Answer:

> An AMI (Amazon Machine Image) is a template used to launch EC2 instances. It contains the operating system, installed software, application code, and configuration. When an AMI is created, AWS takes snapshots of the attached EBS volumes. These snapshots act as a backup of the server's disk, allowing new EC2 instances to be launched with the same configuration and data.

====================================================

### Question:

What does an AMI NOT contain?

### Answer:

An AMI does not contain:

* Running state of the EC2 instance (running processes, RAM contents)
* Public IP address (unless using an Elastic IP)
* Auto Scaling Group configuration
* Load Balancer configuration
* Target Group configuration
* Security Group rules (it stores only the Security Group association if specified at launch, not the rules themselves)
* Route Tables, VPC, Subnets, or other networking resources
* CloudWatch alarms or scaling policies

---

### Question:

When should we create an AMI (backup)?

### Answer:

Usually, an AMI is created:

* Before a production release (so you can roll back if the deployment fails)
* After a successful production release (to save a stable version of the application)
* Before major OS or application updates
* Before patching or maintenance
* Before making significant configuration changes

### Interview Answer:

> We generally create an AMI before a production release as a rollback backup. After the production release is successful and verified, we may also create a new AMI to preserve the latest stable version. If any issue occurs later, we can quickly launch a new EC2 instance from that AMI.

### Question:

What does `systemctl enable nginx` do?

### Answer:

`systemctl enable nginx` configures the Nginx service to start automatically whenever the EC2 instance boots or reboots.

It does not start Nginx immediately. It only enables auto-start.

---

### Difference between `start` and `enable`

```bash
sudo systemctl start nginx
```

* Starts the Nginx service immediately.

```bash
sudo systemctl enable nginx
```

* Configures Nginx to start automatically after every reboot.

```bash
sudo systemctl enable --now nginx
```

* Starts Nginx immediately and enables it to start automatically on future reboots.

---

### Interview Answer:

> `systemctl enable nginx` enables the Nginx service to start automatically whenever the EC2 instance boots. It does not start the service immediately; for that, we use `systemctl start nginx`.

The ALB does not wait another 5 seconds if it already received the response. The timeout is only the maximum wait time.

### Easy way to remember

* Interval (30 sec) = "When should I start the next health check?"
* Timeout (5 sec) = "How long should I wait for a response during this health check?"
